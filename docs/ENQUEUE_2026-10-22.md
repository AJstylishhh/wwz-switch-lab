## Code change / next experimental test

The example routes now enable an opt-in *experimental* \`enqueue\`
handler by default. It returns the schema-grounded protobuf envelope:

\`\`\`text
ServiceResult
  retCode = Success (0)
  ServiceResult_AuthorizationQueueTokenPosition = field 262225376
    data: AuthorizationQueueTokenPosition
      Token:
        Token = ephemeral "wwz-lab-..."
        State = ReadyToDequeue (2)
      Position = 0
\`\`\`

The field type and enum were verified against NSO-embedded descriptors.
The response is still **not accepted/verified on real hardware**.

QueueState uses a random secret to HMAC the original request in memory,
keeps only a digest and an ephemeral token for up to 5 minutes,
reuses the token for identical retries, and caps the cache at 256 entries.
This intentionally does **not** validate platform credentials or
provide real authorization. Unmapped routes still return HTTP 404
so that we can observe the next RPC method.

Run **only the new responder** (not server.py, not p2p_lab.py):

\`\`\`powershell
git pull
py mvp_server.py --host 0.0.0.0
\`\`\`

Existing certs/server.crt and certs/server.key are reused. Default
\`routes.mvp.example.json\` handles both known GUID paths. If a
different \`--routes\` file is supplied, add the Enqueue route there.
